# LazyDesign v0.1-r4 Evaluation Protocol Design

## Goal

Run a fourth six-cell v0.1 evaluation that preserves the r3 experimental inputs and scoring contract while removing tool-interface artifacts from generation. r4 must answer the original question—whether the LazyDesign references improve generated WinUI 3 UI quality—without treating a single benign Remote interface failure as an automatic invalid experiment.

## Scope

r4 changes only the generation execution protocol. It does not change:

- the six baseline/guided scenarios;
- scenario prompts;
- start project and pinned commits;
- guided reference contents or reference set;
- model identifier or reasoning metadata;
- schema-2 `controller-reconciled-v1` harness contract;
- verification templates, runtime checks, scoring rubric, or gate thresholds.

No new harness feature, schema revision, rule engine, reference edit, or source-content repair is part of r4 setup.

- Workspace: `Z:\workspace\LazyDesign`
- Branch: `test/v0.1-r4-evaluation`
- r4 result root: `evaluation/revisions/v0.1-r4/`
- r4 packet root: `evaluation/.runs/v2/v0.1-r4/`

- Start-project commit: `2ffa7d4dcfe76d4ed7671e116bbdbe5d62528e90`
- Model: `GPT-5.6 Sol`
- Reasoning metadata: `not exposed by client`
- Generation network/web access: none
- Generation stopping condition: `PROMPT.md requirements implemented; source frozen before build`

The r4 matrix must be byte-identical to r3 so the experimental inputs remain fixed.

## Controller and generator boundary

### Controller responsibilities

The controller owns all experiment mechanics that do not measure generation quality:

- repository branch, HEAD, worktree, remote, and dirty-state checks;
- packet preparation and packet inspection;
- generation-attempt reconciliation against actual disk hashes;
- controlled build;
- static/runtime/UIA verification;
- canonical `RUN.md` metadata;
- immutable capture;
- structural and execution-readiness validation;
- scoring/report generation only after all six attempts are execution-valid.

The controller never repairs generated source after the generator freezes it.

### Generator responsibilities

Each fresh generation context does only the work needed to produce the requested UI:

1. read the required agent/repository instructions;
2. read the active packet prompt and starter project;
3. for guided cells, read exactly the packet-local references listed in `PACKET.json`;
4. modify only the active packet `project/` source;
5. stop when the fixed generation stopping condition is reached;
6. return the standard 12-item generation report.

The generator does not perform Git repository-state inspection, harness inspection, build, runtime/UIA, capture, validation, scoring, or report generation.

## Normal Remote development tools

Generation may use the normal development interfaces provided by Remote, including:

- Remote file read/write/edit operations;
- PowerShell or CMD;
- ordinary local CLI/file operations needed to edit and inspect the active packet source.

A particular Remote file API is not part of the experiment. r4 measures the generated implementation, not whether one specific file-write interface succeeds on the first request.

## Safety-inspection rule

The rule is narrowed from r3.

A safety inspection must not be deliberately bypassed. The generator must not use obfuscation, encoded payloads, deceptive wrappers, or command transformations whose purpose is to evade a safety decision.

However, a failure of one normal development interface does not prohibit use of another ordinary permitted development interface. For example, a benign file-write request failing in a Remote file API does not by itself forbid a normal PowerShell/CMD or another standard Remote editing path when that path is independently permitted.

The generator records safety-inspection events in its final report. The controller classifies the attempt as `infrastructure_invalid` only when a material external interruption actually prevents the required implementation from being completed and the stopping condition is not reached.

If the generator completes the prompt requirements and reaches the stopping condition despite a non-material tool/safety interruption, the attempt remains `valid` and the interruption is recorded in notes/evidence rather than converted into an invalid experiment.

## What remains forbidden during generation

The generator must not:

- access the web/network;
- read prior baseline/guided captures, scores, reports, or another cell's implementation;
- modify packet prompt, packet manifest, packet references, matrices, evaluation scripts, repository references, historical results, or `evaluation/rehearsal/`;
- run `dotnet build`, app/runtime verification, Windows UI Automation, accessibility verification, capture, aggregate validation, scoring, or reporting;
- repair source after the fixed stopping condition;
- use local Codex CLI, subagents, or parallel agents;
- commit, push, merge, reset, clean, or modify another worktree.

## Attempt classification

The existing schema-2 classification remains unchanged.

### `valid`

Use when generation itself completes as an ordinary model attempt, including cases where the resulting source later fails build or runtime verification. Model-caused compile/runtime defects are quality results and must remain valid attempts.

A transient or non-material tool interruption does not make an otherwise completed attempt invalid.

### `infrastructure_invalid`

Use only when an external infrastructure interruption materially prevents generation from completing the requested source and the fixed stopping condition is not reached. The controller must record concrete evidence and a supported blocker value.

No invalid attempt is replaced or rerun inside the same r4 experiment.

## Verification and immutability

For each returned generation report the controller:

1. recomputes the project delta from packet hashes;
2. writes `generation-attempt.json` from controller-observed state;
3. runs exactly one controlled pinned build;
4. preserves model-caused build failures without source repair;
5. performs runtime/UIA only when the current frozen source produced a successful current build;
6. validates `verification.json`;
7. writes canonical common RUN metadata identical across all six cells;
8. confirms generated-source hashes remain frozen;
9. captures and validates one immutable result;
10. commits only that result directory.

Historical v0.1, r1, r2, and r3 artifacts remain immutable.

## Aggregate gate

After all six r4 captures:

1. all six canonical RUN metadata records must match;
2. `validate-results` must exit 0;
3. `validate-execution` must exit 0 before scoring is allowed.

If `validate-execution` exits 2, preserve all captures and stop before scoring. If it exits 1, treat it as a controller/evidence-contract defect and investigate without modifying captured generated source.

## Success criteria

r4 setup is successful when:

- the r4 matrix is byte-identical to r3;
- all six fresh packets are prepared and `ready`;
- generation prompts describe normal Remote development access and prohibit only genuine safety bypass behavior, not normal alternative development interfaces;
- no experimental content or scoring criteria changed from r3.

The full r4 experiment is execution-ready only when all six immutable attempts pass structural validation and `validate-execution` returns 0. Only then may baseline/guided scoring and the v0.1 gate decision proceed.

## Non-goals

r4 does not fix the r3 `Symbol.Devices` generation defect, modify LazyDesign references in response to r3 outcomes, loosen verification requirements, or manufacture a passing gate. Those are separate decisions after an execution-valid comparison exists.
