# LazyDesign v0.1 Revision and Gate v2 Design

**Date:** 2026-08-07
**Status:** Approved revision direction
**Repository:** `lazyant91/LazyDesign`
**Revision branch:** `docs/v0.1-revision-gate-v2`

## 1. Summary

The first controlled LazyDesign v0.1 comparison is complete and remains an immutable FAIL result. Baseline scored 44/60 and guided scored 46/60. The run exposed three reference defects and two evaluation-procedure gaps that should be corrected before another controlled comparison.

This revision does not broaden the component scope. It keeps the same eight components, five foundations, three scenarios, prompt bytes, starting WinUI project, and scenario-specific guided reference file sets. It revises only the three reference areas implicated by observed failures and introduces a backward-compatible Gate v2 for the next six fresh-context runs.

The original v0.1 result and Gate v1 semantics remain reproducible and are not retroactively reinterpreted.

## 2. Observed problems

### 2.1 Reference problems

The first evaluation identified three concrete guided-output failures that the supplied reference did not prevent:

1. **ListView build failure** — both device-list runs generated a typed-`x:Bind` item model using positional record/init-only properties, producing `CS8852` in generated WinUI XAML type information.
2. **ContentDialog build failure** — both failure-confirmation runs generated `await ContentDialog.ShowAsync()` in a compilation context where the required WinRT await projection/import was unavailable, producing `CS4036` and cascading `MSB3073`.
3. **InfoBar action regression** — the guided failure-confirmation output rendered a Retry `ActionButton` but did not attach `Click`, `Command`, or equivalent activation behavior.

The revision must address these failures with source-backed, narrowly scoped guidance and compile-verified minimal examples. The observed generated failure itself is not sufficient provenance for a new normative rule.

### 2.2 Evaluation-procedure problems

Gate v1 has two mechanical weaknesses:

1. When the baseline overflow-defect count is zero, the current rule always reports the 50% reduction condition as `not demonstrated` and fails. A guided result that also has zero observed overflow therefore cannot satisfy the condition even though it has not regressed.
2. Build failures are recorded as defect counts but are not a mandatory gate prerequisite. In principle, a guided condition could fail to compile in one or more scenarios and still pass the six score/defect conditions.

The revision corrects both without changing the scoring rubric or manufacturing prompts that intentionally force a baseline defect.

## 3. Goals

The revision must:

- preserve the original six captured artifacts, original metrics, original Gate v1 result, and original run matrix unchanged;
- keep the same three task prompts byte-for-byte;
- keep the same pinned starting WinUI project commit and build environment;
- keep the same scenario-specific guided reference **file sets**;
- add source-backed ListView guidance that leads agents toward a build-compatible binding/model pattern without claiming that all C# records are invalid;
- add a compile-verified ContentDialog `ShowAsync()` code-behind pattern appropriate to the pinned WinUI project and explain any required namespace/projection dependency;
- strengthen InfoBar action guidance so an action is not considered complete until activation behavior is wired and verified;
- add Gate v2 zero-baseline overflow non-regression semantics;
- require all three guided generated projects to pass the controlled build before Gate v2 can pass;
- run a completely new baseline 3 + guided 3 comparison in fresh contexts;
- retain exact evidence, immutable capture, rule traceability, and honest `not_run` reporting.

## 4. Non-goals

This revision will not:

- add new WinUI components or foundations;
- add a rule engine, resolver, adapter, static analyzer, custom control library, or Gallery clone;
- change the three task prompts to provoke known failures;
- repair generated evaluation output after generation;
- reuse any of the first six generated artifacts as revision results;
- reinterpret the original Gate v1 result under Gate v2;
- activate Windows Design Kit `ui-kit` evidence without completing its separate component-level inspection;
- add GitHub Actions;
- claim Light, High Contrast, scaled text, Narrator, Accessibility Insights, or other environment checks that were not actually performed.

## 5. Approaches considered

### 5.1 Gate v2 plus targeted reference revision — selected

Revise the three implicated component pages, correct the two gate mechanics, preserve all other experiment inputs, then run six new fresh-context generations.

This has the best continuity with the first experiment while directly addressing observed defects. It also avoids changing the benchmark merely because the first baseline did not contain an overflow defect.

### 5.2 Gate-only revision — rejected

Changing only the gate would isolate evaluation-procedure effects, but it would knowingly leave `CS8852`, `CS4036`, and the inert Retry action unaddressed. That provides little product value and is unlikely to demonstrate that the reference improved.

### 5.3 Prompt/scenario redesign — rejected for this cycle

Making prompts deliberately cause overflow would create a more convenient denominator but would reduce comparability with the first run and risk turning the benchmark into a test tailored to a known failure. Scenario redesign should happen only as a separately approved evaluation version if repeated evidence later shows the current scenarios are not discriminative enough.

## 6. Versioning and immutable history

### 6.1 Preserve the initial evaluation

The following initial-evaluation artifacts remain immutable:

- `evaluation/baseline/`
- `evaluation/guided/`
- `evaluation/results/`
- `evaluation/run-matrix.json`
- captured `PACKET.json`, `RUN.md`, `generated/`, and `evidence/` files

Gate v1 remains available so the existing `44/60 -> 46/60` FAIL can still be reproduced with its original semantics.

### 6.2 Revision namespace

The new controlled comparison uses:

```text
evaluation/revisions/v0.1-r1/
├─ run-matrix.json
├─ baseline/
│  ├─ connection-settings/
│  ├─ device-list/
│  └─ failure-confirmation/
├─ guided/
│  ├─ connection-settings/
│  ├─ device-list/
│  └─ failure-confirmation/
└─ results/
   ├─ metrics.json
   ├─ scores.md
   ├─ findings.md
   └─ gate-decision.md
```

Ignored working packets use a separate revision namespace, for example:

```text
evaluation/.runs/v2/v0.1-r1/{baseline|guided}/{scenario}/
```

`v2` in that path continues to describe the packet contract. `v0.1-r1` identifies the experiment revision and does not imply a packet schema change by itself.

## 7. Versioned run matrix

The initial `evaluation/run-matrix.json` remains unchanged. The revision adds `evaluation/revisions/v0.1-r1/run-matrix.json`.

The revision matrix keeps:

- the same three prompt paths and exact prompt hashes;
- start project commit `b73babad19d0153707a49e5ba1ed9fb0a42c33ef`;
- connection-settings width 420 DIP;
- device-list width 520 DIP;
- the same guided reference path lists for all three scenarios.

Its reference/input commit points to the committed revision reference state. The prompts at that commit must be byte-identical to the original prompts. Only reference contents intentionally changed by the revision may differ.

Every harness command that validates packet or result identity will accept an optional explicit matrix path:

```text
--matrix evaluation/revisions/v0.1-r1/run-matrix.json
```

This applies to `validate`, `prepare`, `inspect-packet`, `inspect-packets`, `build`, `capture`, and `validate-results`. Omitting `--matrix` preserves the current behavior and uses `evaluation/run-matrix.json`, so the initial experiment remains reproducible. The selected matrix must be used for all packet-integrity checks in that command; no command may silently choose the newest matrix.

`evaluation_report.py` will accept the same optional `--matrix` argument and pass it to result validation before generating reports. Revision report generation therefore validates `evaluation/revisions/v0.1-r1/` against the revision matrix, while old report regeneration continues to use the initial matrix by default.

## 8. Gate v2

### 8.1 Backward compatibility

Gate v1 behavior remains unchanged for schema-version-1 metrics and the initial reports.

Gate v2 metrics use `schema_version: 2` and are validated by a new `evaluation/gate-metrics-v2.schema.json`. The existing `evaluation/gate-metrics.schema.json` remains the v1 schema and is not redefined.

### 8.2 Hard build prerequisite

Before the quality conditions can yield PASS, all three guided scenarios must have a successful controlled build.

Mechanically:

```text
guided build failures == 0
```

The report path must cross-check this value against each immutable guided `verification.json` build status so a manually incorrect defect count cannot satisfy the prerequisite.

If any guided scenario has build status `fail` or `not_run`, Gate v2 overall result is FAIL regardless of rubric score.

Baseline build failures remain valid observations. The purpose of the hard prerequisite is to ensure the candidate reference does not advance while its guided outputs are non-buildable.

### 8.3 Score improvement

Keep the existing condition:

```text
guided total improvement >= 20% over baseline total
```

A zero baseline total remains `not demonstrated` rather than automatic PASS.

### 8.4 Overflow condition

Gate v2 has two modes.

When baseline observed overflow defects are greater than zero:

```text
(guided overflow reduction / baseline overflow) >= 50%
```

When baseline observed overflow defects are zero:

```text
guided overflow defects must also be zero
```

This second case is a **non-regression floor**, not evidence of a 50% improvement. Reports must say that overflow reduction was not measurable but the zero-defect floor was preserved.

If baseline is zero and guided is greater than zero, the condition fails.

### 8.5 Remaining quality conditions

Keep the existing conditions unchanged:

- missing anatomy defects decrease;
- missing accessibility defects decrease;
- unnecessary `ControlTemplate` defects do not increase;
- irrelevant XAML/complexity defects do not materially increase;
- every positive guided category delta has at least one specific LazyDesign rule ID and guided evidence.

Gate v2 passes only when the guided-build prerequisite and every quality condition pass.

## 9. Targeted reference revisions

### 9.1 `components/listview.md`

The revision must research the current Microsoft/WinUI guidance for compiled binding and item data models before authoring a new rule.

The final guidance must:

- prevent the observed init-only/compiled-binding build incompatibility in the pinned evaluation environment;
- distinguish a verified safe pattern from a universal ban on records or immutable models;
- keep `ItemsSource`, `ItemTemplate`, selection, and native ListView behavior intact;
- include a minimal model/XAML combination that is compiled in the pinned fixture as part of authoring verification;
- record source IDs and derived reasoning when the safe-model recommendation is an inference rather than an explicit Microsoft requirement.

If official sources do not support a general normative statement, the page must scope the rule to compiled binding in the verified WinUI/.NET environment rather than overgeneralize.

### 9.2 `components/contentdialog.md`

The revision must replace the currently incomplete standalone `ShowAsync()` example with a compile-verified code-behind example for the pinned project.

The guidance must:

- preserve the existing `XamlRoot` requirement;
- show the imports or projection context required for `await ShowAsync()` to compile in the fixture;
- avoid presenting a project-specific import as a universal Microsoft UI-design requirement;
- distinguish dialog UI behavior from C#/WinRT async projection requirements;
- add the observed failure mode to common failures and the verification checklist only when supported by appropriate source/projection documentation;
- compile the minimal example in the pinned fixture before calling it valid.

### 9.3 `components/infobar.md`

The current guidance explains when to provide an `ActionButton` but does not make actual activation a conformance requirement.

The revision must add narrowly scoped guidance that:

- an action intended to resolve or investigate status must have actual invocation behavior through `Click`, `Command`, or an equivalent supported mechanism;
- a visible Retry label without activation behavior is incomplete;
- action activation must be verified, not inferred from XAML anatomy alone;
- keyboard operation remains part of the existing interaction verification;
- the rule cites InfoBar action behavior plus the relevant native command/input evidence and includes derived reasoning if necessary.

## 10. Source acquisition

Implementation begins with source research, not rule wording copied from the observed failures.

Prefer, in order:

1. current Microsoft Learn WinUI/Windows documentation;
2. the pinned WinUI Gallery release/source where executable behavior is needed;
3. other Microsoft documentation specifically required for C#/WinRT projection semantics.

Any newly used source receives a manifest ID, URL, retrieval date, revision metadata when available, scope, and concise notes. Existing source revisions are not silently changed.

No copied documentation pages, large Gallery excerpts, Figma exports, fonts, or credentials are stored.

## 11. Authoring verification before evaluation

Before creating the revision run matrix commit:

- run the structural reference checker;
- compile Python evaluation tooling and run its unit tests;
- compile the ListView minimal binding/model example in the pinned WinUI fixture or a mechanically equivalent isolated fixture;
- compile the ContentDialog `ShowAsync()` example in the pinned WinUI fixture or a mechanically equivalent isolated fixture;
- statically verify the InfoBar example has activation wiring and, where practical, exercise that action in a small runtime check;
- verify the three fixed prompt files are byte-identical to the original prompt commit;
- verify the starting fixture commit remains unchanged;
- verify the guided reference path sets have not changed.

Authoring verification is not scored evaluation evidence. It exists to ensure the reference itself does not publish a known-broken minimal example.

## 12. New six-run comparison

After reference and Gate v2 implementation is committed and pinned by the revision matrix:

1. prepare one new packet per run under the revision packet root;
2. use six separate fresh generation contexts;
3. run baseline and guided with the same model identifier and reasoning configuration;
4. disable network/web during generation for all six;
5. supply no LazyDesign references to baseline;
6. supply exactly the matrix-listed packet-local reference files to guided;
7. perform generation once with no prompt repair, build-feedback repair, or regeneration;
8. freeze generated source;
9. run the controlled build once;
10. record only verification checks actually performed;
11. preserve build failures without repair if they still occur;
12. capture each result immutably under the revision result root.

The user-facing Temporary Chat procedure may be reused, but every run receives a newly prepared revision packet and a new Temporary Chat.

## 13. Scoring and report generation

The same ten 0/1/2 rubric categories and score anchors remain in force. Gate v2 does not change category scoring to make a passing result easier.

Revision metrics live at:

```text
evaluation/revisions/v0.1-r1/results/metrics.json
```

The report generator uses `evaluation/revisions/v0.1-r1/` as its evaluation root, so evidence references retain the existing form:

```text
baseline/{scenario}/...
guided/{scenario}/...
```

Reports must expose:

- baseline and guided totals;
- score improvement percentage;
- overflow mode (`reduction` or zero-baseline `non-regression`);
- guided build prerequisite status and per-scenario build outcomes;
- all quality conditions;
- traceable improvements;
- unchanged defects, regressions, ambiguous decisions, ignored rules, and unnecessary output.

A Gate v2 FAIL remains a valid report-generation outcome and must not trigger source or generated-output repair inside the scored revision artifacts.

## 14. Error handling

- If new source research cannot support the intended normative wording, weaken or omit the rule rather than fabricate authority.
- If a minimal reference example does not compile, do not publish it as valid; fix the reference example before the evaluation input commit is frozen.
- If prompt bytes or guided reference path sets differ from the approved experiment, stop before generation.
- If a revision packet is stale or already used, create a new packet path; do not overwrite it.
- If a generated project fails to build, preserve that failure and continue the evidence/capture path without repair.
- If a run uses a different model/reasoning configuration, intervention, or network policy, exclude it from the controlled six-run set and rerun only in a new fresh context.
- If Gate v2 fails, revise the reference or separately approved evaluation procedure again before adding component scope.

## 15. Testing strategy

Tooling changes require tests for at least:

- Gate v1 zero-overflow behavior remains the original `not demonstrated` FAIL;
- Gate v2 baseline overflow 0 / guided overflow 0 passes the overflow non-regression condition;
- Gate v2 baseline overflow 0 / guided overflow >0 fails;
- Gate v2 positive baseline overflow still requires at least 50% reduction;
- Gate v2 fails when any guided controlled build fails;
- Gate v2 fails when a guided build is `not_run`;
- Gate v2 build prerequisite is cross-checked against captured verification evidence;
- Gate v2 otherwise retains score, anatomy/accessibility, template, complexity, and traceability behavior;
- old matrix/result validation still works against the initial evaluation;
- the revision matrix can prepare and validate packets without changing the initial matrix;
- report generation works from the revision result root and cannot cross evidence namespaces.

Existing harness, gate, evidence, and report tests must continue to pass unless a test is explicitly version-specific and replaced by a backward-compatibility assertion.

## 16. Git and delivery strategy

The initial FAIL branch and PR remain untouched as the record of the first v0.1 candidate evaluation.

Revision design and implementation occur on `docs/v0.1-revision-gate-v2`, which starts at the first evaluation's final commit. Do not merge either branch without repository-owner approval.

The revision should use reviewable commits for:

1. approved design and implementation plan;
2. Gate v2/versioned-evaluation tooling with tests;
3. source research and targeted component-reference revisions;
4. authoring compile verification and pinned revision matrix;
5. baseline revision results;
6. guided revision results;
7. Gate v2 scoring and decision;
8. final review/PR update.

If Gate v2 passes, the final PR may supersede the initial FAIL PR after explicit repository-owner approval. If Gate v2 fails, both results remain preserved and precision expansion stays blocked.

## 17. Definition of done

This revision cycle is complete only when:

- Gate v2 and versioned matrix support are implemented and tested without changing Gate v1 meaning;
- the three targeted component references are source-backed and their minimal implementation patterns are authoring-verified;
- original prompts and starting fixture remain unchanged;
- six new fresh-context revision runs are immutably captured;
- all revision results validate against the revision matrix;
- Gate v2 reports are generated from revision metrics;
- the guided-build prerequisite and every quality condition are mechanically evaluated;
- the final PASS or FAIL is reported without unsupported verification claims;
- no additional component family is started unless Gate v2 passes and the repository owner separately approves expansion.
