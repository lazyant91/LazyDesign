# LazyDesign v0.1-r3 Clean Evaluation Design

## Context

v0.1-r2 produced six immutable captures, but the experiment could not reach the intended execution-readiness result for two independent reasons:

1. `guided / device-list` was materially interrupted by Remote safety inspection and was correctly captured as `infrastructure_invalid` with `stopping_condition_reached=false`.
2. The controller wrote different `Tool access` strings into otherwise comparable `RUN.md` records. Two runs omitted `Windows UI Automation` because runtime verification was not performed, while four runs included it. `validate-results` therefore failed with `Tool access differs across the six runs` before execution readiness could classify the experiment.

r2 is immutable and remains an evaluation result. r3 must not repair, replace, or rewrite any r2 capture.

## Goal

Run a new six-cell schema-2 evaluation that preserves the exact r2 prompts, references, start fixture, model metadata, generation stopping rule, and comparison rubric while eliminating controller-authored RUN metadata drift.

A valid r3 experiment has one of two structural outcomes:

- all attempts are execution-valid, `validate-results` and `validate-execution` both exit 0, then scoring may begin; or
- one or more attempts are genuinely infrastructure-invalid, `validate-results` exits 0 and `validate-execution` exits 2, then the experiment ends as `INCOMPLETE` without scoring.

`validate-results` or `validate-execution` exit 1 is a controller/evidence-contract defect that must be investigated without modifying generated source or immutable captures.

## Approaches considered

### A. Repair r2 captures

Rejected. r2 captures are immutable by design. Editing their `RUN.md` files would destroy the evaluation record and violate the versioned experiment contract.

### B. Add a new harness schema or a matrix-level metadata subsystem

Rejected for r3. A new schema could encode canonical controller metadata and make drift impossible, but it introduces implementation and regression risk unrelated to the UI-reference comparison. The existing schema-2 validator already detects inconsistent metadata.

### C. New r3 experiment with frozen controller metadata and a pre-capture guard

Selected. Reuse the current schema-2 execution contract unchanged and define the common RUN metadata values before the first generation. Before each immutable capture, compare the packet RUN fields against those canonical values. Controller metadata errors may be corrected only before capture; generated source remains frozen.

This is the smallest change that addresses the r2 controller defect without changing the experimental inputs or harness semantics.

## Fresh-generation protocol

Baseline contexts may read only the packet prompt and start project, with `PACKET.json` limited to identity/status information.

Guided contexts may additionally read exactly the references listed in `PACKET.json`. Prepared packet copies live under `<PACKET>/context/<reference path>`; repository-source reference files and any previous evaluation result are out of bounds.

Generation contexts do not run build, runtime, UIA, accessibility, capture, scoring, or evaluation validation commands.

If a Remote safety inspection blocks a source edit that is required to finish the implementation, the generator must not disguise or bypass that blocked operation. It records the event accurately. The controller decides whether the event materially prevented generation. A blocked call that has no effect on the final implementation and does not prevent the stopping condition may remain a valid attempt; a block that leaves required source unapplied and prevents the stopping condition is `infrastructure_invalid / remote_safety_inspection`.

## Controller reconciliation and verification

After each generation:

1. Recompute the project delta from packet hashes rather than trusting self-report.
2. Write `generation-attempt.json` with the exact controller-derived delta and validity decision.
3. Run `inspect-packet` and require no evidence-contract error.
4. Run the controlled pinned build on the frozen source.
5. Perform available runtime/UIA verification only when the built implementation can actually be exercised; never use a stale binary after a failed build.
6. Write `verification.json` using distinct static, build, rendered runtime, UIA, theme, and not-run evidence.
7. Write `RUN.md` using the canonical common metadata above plus cell-specific artifact metadata.
8. Before capture, run a controller metadata guard that checks the common RUN fields against the exact canonical strings.
9. Require `inspect-packet` to report `capture_ready`.
10. Capture once and never modify that result afterward.

Verifier/evidence scripts may be corrected before capture when the generated source is unchanged and the correction only fixes controller observation logic.

## Pre-capture metadata guard

For each packet, before `capture`, parse `RUN.md` and require exact equality for all canonical fields. The guard must fail before immutable capture if any common field drifts.

After all six captures, independently compare those same fields across all results before running the official aggregate validators. This is a diagnostic guard only; `validate-results` and `validate-execution` remain the authoritative gates.

## Execution-readiness and scoring

After six captures:

1. `validate-results` must exit 0.
2. `validate-execution` determines whether scoring is allowed.
   - exit 0: proceed to the unchanged ten-category scoring/report workflow.
   - exit 2: preserve the experiment as `INCOMPLETE`; do not create metrics or reports.
   - exit 1: stop and investigate the controller/evidence contract; do not score.

A model-caused build/runtime defect is a valid quality result and does not by itself make execution invalid. A material external infrastructure interruption does.

## Success criteria

Preparation is complete when:

- the r3 matrix validates;
- its input commit, start project, scenarios, prompts, widths, and references are mechanically identical to r2;
- all six r3 packets are freshly prepared and report `ready`;
- canonical controller metadata is documented before generation starts.

The experiment is complete only after all six immutable captures exist and the aggregate structural/execution gate has been run. Scoring is permitted only when execution readiness exits 0.
