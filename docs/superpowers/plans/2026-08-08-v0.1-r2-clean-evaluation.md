## Task 1: Controller packet preparation

For each cell, prepare a new packet with the r2 matrix:

```powershell
python scripts/evaluation_harness.py prepare `
  --condition <baseline|guided> `
  --scenario <scenario> `
  --destination evaluation/.runs/v2/v0.1-r2/<condition>/<scenario> `
  --matrix evaluation/revisions/v0.1-r2/run-matrix.json
```

After all six are prepared, run:

```powershell
python scripts/evaluation_harness.py inspect-packets `
  --root evaluation/.runs/v2/v0.1-r2 `
  --matrix evaluation/revisions/v0.1-r2/run-matrix.json
```

Require all six packets to report `ready` before opening any fresh generation context.

## Task 2: Fresh-context generation

For each cell:

1. Open a genuinely fresh model context.
2. Supply only the packet-local generation inputs allowed by the condition.
3. Do not require the generation context to invoke `evaluation_harness.py inspect-packet`; controller preflight already established packet readiness.
4. Do not enable web/network access.
5. Allow source edits only inside that packet's `project/` directory.
6. Stop generation when the fixed stopping condition is reached or when the model itself ends the implementation attempt.
7. Do not build, repair, or rerun source from the generation context unless the fixed generation protocol explicitly permits the same tool access for all six cells.
8. Record the model identifier and the client-visible reasoning metadata exactly. If the client still exposes no reasoning label, record `not exposed by client`.

## Task 3: Controller reconciliation after each generation context

After the fresh context returns, the controller—not the generator—must inspect actual disk state.

Create `evidence/generation-attempt.json` with:

- `condition` and `scenario` matching the packet;
- `validity: valid` when no external infrastructure event materially interrupted generation;
- `validity: infrastructure_invalid` only for a concrete Remote/platform/tool infrastructure blocker;
- exact blocker enum;
- whether the fixed stopping condition was reached;
- exact changed/deleted project delta derived from the packet filesystem;
- concrete evidence paths for any infrastructure-invalid attempt;
- a concise reason based on observed tool outcomes and disk state.

If model self-report and disk state disagree, preserve disk state and use the controller-derived delta.

Run `inspect-packet` again. A missing or contradictory generation-attempt record must keep the packet out of `capture_ready`.

## Task 4: Controlled build and verification

Build only through the pinned helper:

```powershell
python scripts/evaluation_harness.py build `
  --packet evaluation/.runs/v2/v0.1-r2/<condition>/<scenario> `
  --matrix evaluation/revisions/v0.1-r2/run-matrix.json
```

Then perform available runtime/UI Automation verification against the frozen generated source.

- Build pass is not rendered verification.
- Runtime failure is preserved, not repaired.
- Verification selectors/evidence tooling may be corrected only when generated source is unchanged and the change does not alter the implementation under test.
- Complete `verification.json` with exact evidence/reasons.
- Copy artifact-derived RUN metadata from `inspect-packet` into `RUN.md`.
- Require `capture_ready` before capture.

## Task 6: Execution-readiness gate

After all six captures exist:

```powershell
python scripts/evaluation_harness.py validate-results `
  --root evaluation/revisions/v0.1-r2 `
  --matrix evaluation/revisions/v0.1-r2/run-matrix.json

python scripts/evaluation_harness.py validate-execution `
  --root evaluation/revisions/v0.1-r2 `
  --matrix evaluation/revisions/v0.1-r2/run-matrix.json
```

Interpret `validate-execution` as:

- exit `0`: all six attempts execution-valid; proceed to scoring;
- exit `2`: structurally valid but infrastructure-incomplete; preserve captures and stop before metrics/report generation;
- exit `1`: invalid matrix/capture/evidence; investigate the evaluation data contract without repairing generated source.

If exit 2 occurs, v0.1-r2 ends as `INCOMPLETE`. A new experiment version is required for another six-run attempt.

## Task 7: Score only an execution-ready experiment

Only after `validate-execution` exits 0:

1. score all six captures with the unchanged ten-category rubric;
2. write schema-version-2 metrics under `evaluation/revisions/v0.1-r2/results/metrics.json`;
3. preserve scenario-local score evidence, defect counts, rule traces, and all findings sections;
4. run:

```powershell
python scripts/evaluation_report.py `
  evaluation/revisions/v0.1-r2/results/metrics.json `
  --output-dir evaluation/revisions/v0.1-r2/results `
  --matrix evaluation/revisions/v0.1-r2/run-matrix.json
```

The report command must not be used to score an execution-incomplete experiment. Gate v3 means execution readiness first, then the existing Gate v2 quality formula and guided-build prerequisite.
